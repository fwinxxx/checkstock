# CheckStock

Небольшое приложение для учёта товара на складах фулфилмента. Показывает остатки, резервы FBS и отправки: что лежит на складе, что доступно и что уже в пути.

Python 3.12 · FastAPI · PostgreSQL 17.

[Видео демонстрации — 3:26, MP4](https://github.com/fwinxxx/checkstock/releases/download/v1.0.0/checkstock-demo.mp4)

## Запуск

Понадобится запущенный Docker с Compose v2. При первом запуске зависимости скачаются автоматически.

```bash
docker compose up --build -d --wait
```

Приложение: [localhost:8000](http://localhost:8000). Документация API: [localhost:8000/docs](http://localhost:8000/docs).

База и тестовые данные создаются при запуске. Повторный запуск сохраняет изменения и не дублирует приходы. Если порт занят, задайте другой: `CHECKSTOCK_PORT=8002 docker compose up -d --wait`.

Остановить приложение: `docker compose down`. Посмотреть логи: `docker compose logs --tail=100 app db`.

## Тестовые данные

Один магазин, два склада и три товара из задания:

| Артикул | Товар | Север | Юг |
|---|---|---:|---:|
| SKU-101 | Органайзер | 10 | 6 |
| SKU-102 | Контейнер | 5 | 0 |
| SKU-103 | Корзина | 0 | 4 |

Начальные 25 единиц заведены через приходы, поэтому их можно увидеть в истории.

## Как устроен учёт

**Доступно = на складе − резерв FBS.** Резерв оставляет товар на ФФ, но блокирует его для других отправок. При отмене товар снова доступен, при отправке — списывается с ФФ и переходит в путь к клиенту.

**Отправка и приёмка разделены.** При перемещении товар сначала покидает исходный склад и только после приёмки появляется на целевом. FBO после приёмки учитывается на маркетплейсе. Так одна единица не считается одновременно в двух местах.

**Нехватка проверяется на выбранном складе.** Если на Юге доступно 6 единиц, отправить с него 8 нельзя, даже если на Севере есть запас. Приложение покажет, где есть товар, и предложит сначала переместить его.

**Удаление склада — это архивирование.** Остатки остаются на нём, история сохраняется. Новые приходы, резервы и FBO с архивным ФФ запрещены. Начатые операции можно завершить, свободный товар — вывезти на активный склад, сам ФФ — восстановить. Архивный запас входит в общие итоги с отдельным предупреждением.

**Повторное подтверждение ничего не списывает.** У запроса есть UUID, а у отправки — статус. Повтор возвращает прежний результат или сообщает, что действие уже выполнено. Если ответ потерялся, в той же вкладке можно восстановить запрос после перезагрузки.

Остатки, статус и история сохраняются одной транзакцией PostgreSQL. Блокировка строки магазина защищает от одновременного списания одного запаса. Это простое решение для объёма тестового; при росте нагрузки блокировку можно сузить до конкретных товаров и складов.

На экране также сверяется общий баланс: весь принятый товар должен находиться на ФФ, в пути, на маркетплейсе или у клиента. Резерв входит в остаток ФФ и второй раз не прибавляется.

## Проверка

```bash
docker compose --profile test run --build --rm tests
```

Тесты используют отдельную PostgreSQL-базу и не меняют данные приложения. Проверяют приходы, резервы, перемещения, нехватку, архивирование, повторы, одновременные запросы и откат при ошибке записи.

Подробнее: [результаты и браузерная проверка](docs/verification.md).

## Ограничения

Один артикул в операции, целые штуки и полная приёмка отправки. Возвраты, частичная приёмка, авторизация и подключение реальных API маркетплейсов не реализованы. Названия заказов и складов МП вводятся вручную. Приложение запускается локально.
